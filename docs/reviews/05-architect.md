# 架构师 审查报告

## 审查范围与视角

从系统架构维度审查：四宿主（Bun / Cloudflare Workers / Vite dev / EdgeOne）对 `createAppHandler` 的复用一致性、前后端类型契约的同构性与漂移风险、新增 LLM 平台的扩展成本（shotgun surgery）、前后端解耦（硬编码接口、status 契约不全）、以及三条部署路径的配置漂移。

取证文件：`server/app.ts`、`server/multi.ts`、`server/{volc,aliyun,tokenplan,zhipu,deepseek,gitee,balances,plans}.ts`、`server/index.ts`、`worker/index.ts`、`vite.config.ts`、`cloud-functions/api/[[default]].js`、`.edgeone/cloud-functions/api-node/*`、`wrangler.toml`、`edgeone.json`、`src/{types,api}.ts`、`src/App.vue`、`.env.example`、`.dev.vars.example`。

正面结论先行：`createAppHandler(env: EnvGetter)` 的抽象方向是正确的——用 `EnvGetter` 把环境读取与宿主解耦，签名层统一用 Web Crypto 兼容四宿主，多账号 `readKeys`/`readKeyPairs` 是干净的可复用原语。问题集中在**抽象没有贯彻到位**：各宿主在构造时机、类型校验、回退、错误兜底上各自为政；前后端类型完全手工双写，无单一事实源。

## 总结与优先级建议

**核心架构判断**：抽象方向（平台无关 `createAppHandler` + `EnvGetter` + Web Crypto 签名 + 多账号原语）是健康的、值得在重构中保留的资产；问题不在抽象本身，而在**抽象未贯彻一致**与**缺乏单一事实源**。

按优先级分三档：

**第一档（P1，重构前应优先确立的架构基线）：**

1. **前后端类型单一事实源**（P1×2 条）：把 ~20+ 双写类型与核心 `AccountEnvelope` 收敛到共享层。这是后续一切重构（含本次 tdesign-mobile→tdesign-vue-next 迁移）的安全网——没有它，迁移期间任何字段改动都可能前后端静默失配。**建议作为重构第 0 步**。
2. **provider 注册表化**（P1×2 条）：消除 7+ 文件 shotgun surgery 与 5 处硬编码清单同步。这是扩展性的根因；重构正好顺势引入声明式 provider 描述符，让 status/路由/前端渲染全部数据驱动。
3. **status 契约补全**（P1）：纳入全部 provider，前端 providerTags 改为数据驱动——直接利好本次"屏效/自适应"重构（标签区不再写死 5 项）。
4. **四宿主一致性**（P1×2 条）：统一 `createAppHandler` 构造时机与 env 类型规整，消除 Worker/EdgeOne 每请求重建 + 类型防御不均的隐性分歧。

**第二档（P2，重构中顺带收敛）：** 5. EdgeOne 双产物去歧义 + SPA 回退/部署声明对齐三宿主。6. 生产宿主错误兜底与 Vite 对齐。7. 两份 env 样例合并；`error` 字段名去重载；`EquityQuota`/`TokenPlanEquity` 统一命名；前端 `refresh` 数据驱动化；超时语义对齐评估。

**第三档（P3，细节清理）：** 8. 删除 `InferenceUsage.columns` 死计算；dispatcher 改查表；`keyHint` 契约固化。

**对本次重构的直接启示**：tdesign-mobile→tdesign-vue-next 是前端层替换，但若不同时确立"类型共享 + provider 注册表"，新 UI 仍会继承当前的硬编码 9 接口与 5 处清单同步债务，迁移只是把同一套耦合换一层皮。建议重构顺序：先做第一档 1-2（类型共享 + 注册表），再换组件库，则新 UI 天然数据驱动、扩展零成本。
