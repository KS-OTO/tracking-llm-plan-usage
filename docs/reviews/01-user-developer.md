# 用户/开发者 审查报告

## 审查范围与视角

从「日常使用这个仪表盘 + 阅读/维护这套代码」的双重视角，覆盖全栈全流程：

- **部署/运行体验**：README 与 package.json 命令是否吻合；`.env` / `.dev.vars` / wrangler 配置是否易错；四个宿主（Bun / Workers / Vite dev / EdgeOne）入口行为是否一致。
- **代码可维护性**：server 各客户端的签名/请求/解析样板是否可抽取；前后端类型是否重复导致漂移；App.vue 的 refresh 编排是否可持续维护。
- **契约一致性**：前端 `src/types.ts` 与 server 实际返回结构（尤其错误账号对象）是否吻合。
- **文案一致性**：README 表格、组件标题、空状态、错误提示前后是否统一。

> 审查方式：逐文件 `read` 取证，所有问题给出 `文件:行` 定位。以下问题均为真实发现，不为凑数。

## 总结与优先级建议

### P1（迁移前应解决，阻塞可维护性）

1. **`AccountEnvelope<T>` 类型谎言**（契约项）——这是全站可维护性的根因：错误账号实际不含 `T` 字段但类型声称恒在，导致 5 个组件被迫行内重声明数据 shape + 遍地防御性 `?.`。迁移到 tdesign-vue-next 时应首先改为 discriminated union，一改消百处。
2. **前后端类型重复 + 命名不一致**（`src/types.ts` vs server 各模块）——趁重构建立共享类型层，否则迁移后漂移面更大。
3. **server 端三组重复样板**：`toNumber` × 3（已漂移）、`sha256Hex`/`textEncoder` × 3、fetch-JSON-错误提取 × 4——迁移前抽取共享 util，减少模板复制。
4. **两处死代码**：`SectionCard.vue`（整文件未引用 + 引用不存在的 token）、前端 `maskKey`（仅测试引用）——直接删除。

### P2（迁移中顺手修正）

5. README 简介/目录结构行/footer 文案与实际功能范围不一致。
6. `.dev.vars.example` 缺扩展平台变量；裸 `vp` 命令文档风险。
7. `onModelInput` 全量刷新 + 无防抖；`totalsOf` 重复计算；provider 显示名双写。
8. 时间戳单位归一化策略不统一；`/api/status` 不含扩展平台。

### P3（细节，择机处理）

9. Coding Plan 窗口百分比重复显示（实为 UI bug，建议提为 P2）；deploy 命令描述简化；迁移后更新组件库标注。

**总体评价**：代码工程质量较高——多账号容错（`Promise.allSettled` + `runAccounts`）、四宿主复用 `createAppHandler`、Web Crypto 签名跨平台兼容等设计扎实。主要技术债集中在**类型契约**（`AccountEnvelope` 类型谎言 → 组件被迫行内重声明）和**样板重复**（server 端 3 组重复 helper），两者都应在 tdesign-vue-next 迁移中一并治理。文案层面整体一致性好，少数遗漏不影响使用。
