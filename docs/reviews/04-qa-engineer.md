# 测试工程师 审查报告

## 审查范围与视角

本人以测试工程师视角，审查本仓库**测试覆盖的充分性**与**代码的可测性**，覆盖全栈全流程：

- 既有测试基线：6 个 `server/*.test.ts` + 1 个 `src/__tests__/utils.spec.ts`，共 **43 个 `it()` 用例**（实测计数，与任务描述一致）。测试仅覆盖纯函数层：签名向量（`sign.ts`/`aliyun.ts`）、多账号 env 读取（`multi.ts`）、解析器（`plans.ts`/`balances.ts`）、前端工具（`utils.ts`）。
- 未被测试的代码面：`server/app.ts`（432 行请求分发核心）、全部 fetch 客户端（`deepseek/gitee/volc/zhipu/tokenplan/aliyun` 的网络层）、`src/api.ts`（前端请求封装）、`src/App.vue`（编排逻辑）、9 个 Vue 组件。
- E2E / 集成测试：**完全缺失**（无 `e2e/`、无 Playwright、无跨宿主集成测试）。
- 测试规范：对照 `tests` skill 的断言/结构约定（`toBe`/`toStrictEqual`、单 `describe`、禁 `toMatchObject`/`toHaveLength`）核对现状。
- 测试基础设施：CI、coverage 门槛、脚本约定、死依赖。

取证方式：逐文件 `read` 源码与测试、`grep` 断言风格与 `vi.*` mock 用法、`glob` 确认 CI/E2E 缺位、统计 `it()`/`describe()` 计数。所有结论附文件:行定位。

> 总体判断：**测试金字塔严重头重脚轻**。底层签名/解析（确定性最高、最易测的部分）覆盖良好且用真实 golden vector；但**中间的请求分发/错误编排层（`app.ts`）和网络容错层零覆盖**，而这两层恰恰是多账号独立容错、密钥掩码、错误对象契约等业务核心逻辑所在。前端侧完全裸奔。当前重构（tdesign-mobile → tdesign-vue-next、响应式/暗色/适老化）若无组件/E2E 测试兜底，将处于"改了不知对错"的高风险状态。

## 总结与优先级建议

### 覆盖率结构画像

```
            ┌─ 签名向量 (sign/aliyun)   ████████ 强 (golden vector)
            ├─ env 读取 (multi)          ███████░ 强
纯函数层 ──┼─ 解析器 (plans/balances)   ██████░░ 中 (漏错误路径/边界)
            └─ 前端 utils               █████░░░ 中 (漏 formatDateTime/边界)
            ┌─ app.ts 分发/编排/错误契约 ░░░░░░░░ 零  ← 业务核心、四宿主共用
            ├─ 各 fetch 客户端网络层     ░░░░░░░░ 零  ← 解析耦合 fetch 不可测
集成/编排 ─┼─ src/api.ts 四错误分支     ░░░░░░░░ 零  ← fetch 硬编码难注入
            ├─ App.vue refresh/apply     ░░░░░░░░ 零  ← 闭包不可测
            └─ 9 个 Vue 组件三态渲染     ░░░░░░░░ 零  ← 含未导出纯逻辑
E2E        └─ 响应式/暗色/空态/连通       ░░░░░░░░ 零  ← 重构目标维度全无兜底
```

**核心矛盾**：测试投在最易测、确定性最高的底层，而**多账号容错契约（`runAccounts` 的 `{keyHint,error}` 形态）、密钥掩码安全契约、跨宿主 EnvGetter 差异、前端错误文案分支——这些真正会因重构而回归的业务逻辑，零覆盖。**

### 优先级排序

**P0（重构前必须补，否则"盲改"）**

1. `app.ts` 的 `runAccounts` 多账号错误对象契约 + `dateRange` 边界（第一节）。这是前端 `AccountEnvelope` 类型和用量明细数据正确性的唯一真相源。
2. server 端 `maskKey`（`app.ts:74`，与 `src/utils.ts` 重复但**未被测**）——密钥不泄露的安全契约。建议先去重（删 server 副本、复用 utils），再补测试。

**P1（重构同步落地）** 3. 给 9 个组件补 props→输出契约测试（`@vue/test-utils` 已就绪），尤其锁定 `codingWindowLabel`/`windowStatus` 告警色阶与 `rowsOf`/`totalsOf` 求和逻辑（第四节）。4. `src/api.ts` 四错误分支契约测试——重构 fetch 注入缝或用 `vi.stubGlobal`（第四节）。5. 把 `deepseek`/`gitee`/`volc`/`zhipu`/`tokenplan`/`aliyun` 的解析从 fetch 中剥离导出，补单测（第二节）——这是用最小代价拿到最大覆盖的结构性修复。6. 引入少量 Playwright E2E 覆盖空态/暗色/连通（第五节），对齐重构目标。7. 给 `createAppHandler` 端到端集成测试（路由/404/500/503/ERROR_HINTS 文案）。

**P2（质量基线）** 8. 断言风格对齐 `tests` skill：`balances.test.ts` 的 `toMatchObject`→`toStrictEqual`、各文件收敛单 `describe`、补签名 golden 精确值（第三、六节）。9. 加 coverage 门槛 + 最低 CI（`test:unit`+`type-check`+`lint`）+ `test`/`test:e2e` 脚本（第六节）。

**P3（收尾）** 10. `utils.spec.ts`→`utils.test.ts` 并移至 `src/`；补 `formatDateTime`/maskKey len9/formatReset 临界用例；`.toEqual`→`toStrictEqual`。

### 重构测试策略建议

重构（mobile→desktop、加响应式/暗色/适老化）**前**应先建立"特征测试（characterization test）"基线：对现有 9 个组件的 props→关键输出做快照式契约测试，锁定"重构前的正确行为"；迁移到 `tdesign-vue-next` 时这些测试作为回归网。否则在零组件测试 + 零 E2E 的现状下推进桌面端迁移，"改完不知道对不对"是必然结果。
