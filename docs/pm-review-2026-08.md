## 执行摘要

重构把「能用」做扎实了：三 Tab 分组、暗色、骨架屏、多账号独立容错、防抖过滤、后台暂停轮询都落地了，工程质量在同类自托管工具里属上乘。但产品的灵魂问题没解——**「哪个号快用完了」依然要逐 Tab 逐卡滚动人工找**，全页没有任何汇总/预警层，监控工具「一眼看异常」的核心价值尚未成立。其次是**首启无 Key 时满屏红色错误横幅**，错误态与空态语义混淆，新用户第一印象是「坏了」而不是「待配置」。旧审查（`docs/reviews/02-product-manager.md`）列出的 5 个 P1 里有 3 个（Token Plan 单位、半配置静默丢弃、按账号错误中文化）原样未修，属于已知问题带病上线。下一轮迭代应把「摘要 + 预警」和「账号别名」作为主线，而非继续加平台。

## 发现的问题

### P0 严重

**P0-1 核心场景「哪个号快爆了」没有一眼答案——全页无汇总与预警层**

- 【证据】`src/App.vue:118-128` 顶栏 provider 标签只显示「平台 ×账号数」，不含任何健康状态；`App.vue:41-78` 的 `providerTags` 计算属性只读 `count/configured` 两个字段。用量 ≥90% 的红色进度只存在于卡片内部（`utils.ts:65-73` `progressStatus` 在 ≥90 时返回 error），重置倒计时也只散落在各窗口块（`VolcPlanSection.vue:123` 等）。用户要回答「哪个号快用完、哪个先重置」，必须切 3 个 Tab、滚动每个平台卡片、自己横向对比——8 个区块 × 多账号时这是几十次视觉定位。旧审查 P2「顶部增加摘要条」明确提出过，未落地。
- 【影响】这是监控类工具的第一价值。现在的产品是「数据展示面板」而非「监控仪表盘」：数据全但洞察为零。重度多账号用户（本项目明确画像）每天要做的人工扫描成本最高。
- 【建议】顶栏下加一条「健康摘要」：N 个窗口用量 ≥80%/≥90% 徽标（点击跳对应卡片）、最近一次重置倒计时 Top1、按币种合计可用余额、M 个资源包 7 天内到期。数据前端已有（全部 slice 都在 store 里），纯前端聚合即可，无需后端改动。

**P0-2 首启无 Key = 红色错误横幅墙，错误态与空态语义混淆（旧 P1 未修）**

- 【证据】未配置时后端返回 503（`server/app.ts:264-267,237-239` 等，code=`NOT_CONFIGURED`），前端 `applyResult` 把它当普通错误写入 `error`（`dashboard.ts:36-42`）。`AccountSection.vue:30-38` 的分支逻辑里，`empty` prop 来自 `data?.accounts.length === 0`（如 `DeepSeekSection.vue:21`）——但 503 时 `data` 恒为 `null`，`empty` 恒为 false，于是走 `v-else` 分支渲染 `<t-alert theme="error">`。**专门设计的 `t-empty` 空态分支（`AccountSection.vue:36` + 各 Section 的 `empty-text`）在「未配置」这条路径上永远不可达**（服务端只要没配 Key 就 503，不存在 200 + 空数组的返回）。首屏「套餐订阅」Tab 即呈现 4 条红色错误横幅。`e2e/dashboard.spec.ts:34-37` 断言的「未配置 VOLC_ACCESS_KEY_ID / VOLC_SECRET_KEY」文本实际匹配的是红色 alert 里的 503 message，测试名义上叫 empty states，验证的却是错误态。
- 【影响】「未配置」是正常的初始状态，不是故障。红色 error 语义会劝退新用户（「部署失败了？」），也和 README 宣称的「骨架屏/错误告警/空状态统一承载」不符。E2E 还在为错误的行为背书。
- 【建议】前端对 `code === 'NOT_CONFIGURED'` 单独处理：渲染中性 `t-empty`（现有的 `empty-text` 文案已经是为此写的，接上即可），并在全部 provider 未配置时展示一张引导卡（.env 配置说明 + 各平台 Key 获取链接）。E2E 相应改为断言空态组件而非错误文本。

### P1 重要

**P1-1 账号唯一标识是掩码 Key，多账号用户根本分不清哪个号是谁**

- 【证据】所有区块的账号标签都是 `account.keyHint`（如 `VolcPlanSection.vue:87`、`DeepSeekSection.vue:35`），服务端 `keyHint = maskKey(key)`（`server/app.ts:49-54,270`），即 `AKLT****abcd` 形态。`server/multi.ts` 与环境变量体系（README:67-72）均无别名/备注机制。
- 【影响】产品画像就是「同时订阅多家 Coding Plan 的多号玩家」，而回答「哪个号快用完」的前置问题是「这个 `sk-7****f3c2` 是我的大号还是小号」。用户只能靠记忆掩码尾缀，账号一多（3 个以上）即不可用。这直接削弱 P0-1 摘要层的价值——摘要里列出一堆掩码 Key 没有意义。
- 【建议】支持可选别名变量（如 `DEEPSEEK_LABEL_2=公司号`，与 `_N` 同编号配对，复用 `readPairedMap` 模式），无别名时退化为「账号 N + 掩码」。后端 `runAccounts` 注入 `label` 字段，前端卡片头展示。成本很小，收益极大。

**P1-2 模型过滤防抖已修，但每次过滤仍全量重发 9 个接口**

- 【证据】`dashboard.ts:109-115` `onFilterInput` 防抖后调用 `refresh()`，而 `refresh()` 是 `Promise.allSettled` 一次发全部 9 个 API（`dashboard.ts:75-85`），包括与模型过滤毫无关系的 deepseek/zhipu/aliyun/gitee/extras。
- 【影响】过滤只影响火山推理一个接口（`api.volcInference`，`api.ts:81-86`）。用户在过滤框每敲一次词（400ms 防抖后），全平台多账号凭据被无谓地再打一遍，浪费限流配额、拖慢响应。旧审查 P1「过滤只调 volcInference」只修了一半。
- 【建议】过滤走独立轻量刷新（只调 `api.volcInference`，单独更新 `volcInference` slice）；更进一步可考虑本地过滤，但火山接口本身支持 `ModelName` filter（`server/app.ts:383-389`），服务端过滤 + 局部刷新即可。

**P1-3 信息架构按「数据类型」分 Tab，但智谱卡片横跨两类，自相矛盾**

- 【证据】「余额账户」Tab 放 DeepSeek/阿里云资源包/模力方舟（`App.vue:168-192`），但智谱的**余额 + 资源包**却在「套餐订阅」Tab 的智谱卡片内（`ZhipuSection.vue:176-241`：余额 Statistic×5 + 资源包 Table）。用户想「看所有余额」时，余额 Tab 里没有智谱；想在套餐 Tab 专注额度时，智谱卡里混着四行金额。
- 【影响】Tab 分组的心智模型是「订阅看额度、余额看钱」，智谱破坏了这个契约。找智谱余额平均要多一次 Tab 切换 + 卡内滚动。
- 【建议】短期：把智谱卡片拆为「智谱 Coding Plan」（订阅 Tab）与「智谱余额/资源包」（余额 Tab）两卡，数据同源一次拉取；长期见路线图 P2 的「按平台重组」实验。

**P1-4 Token Plan 额度无单位，token/credits/元混淆（旧 P1，原样未修）**

- 【证据】`TokenPlanSection.vue:25-26` 列头只有「总额度/剩余」，`:160-161` 用 `formatTokens` 渲染成 `1.20M` 形态。README:26 明确该值是 CREDITS。同页其他地方的 `formatTokens` 全部表示 token 数（如 `VolcUsageSection.vue:119`）。
- 【影响】同一格式化函数两种语义，用户无法判断「1.20M」是 token 还是 credits，更无法与人民币金额的阿里云资源包区分。这是旧审查点名的问题，重构后未动。
- 【建议】列头改「总额度(CREDITS)」或副标题注明「额度单位为 CREDITS，非 token/人民币」。一行文案的事。

**P1-5 成对凭据半配置被静默丢弃（旧 P1，原样未修）**

- 【证据】`server/multi.ts:51-56`：`readKeyPairs` 遇到只有 key 没 secret（或反之）的组直接跳过，无任何结构化提示。用户填了 `VOLC_ACCESS_KEY_ID` 漏填 `VOLC_SECRET_KEY` 时，页面显示「未配置」。
- 【影响】「我明明配了为什么说没配」是真实的配置陷阱，排查成本高（要读源码才知道规则）。
- 【建议】`/api/status` 增加 `incomplete` 数组（检测单边存在的变量名），前端在对应区块提示「检测到 AccessKey 但缺少 SecretKey」。

**P1-6 按账号错误直出原始英文 message（旧 P1，原样未修）**

- 【证据】`server/app.ts:111-112`：`runAccounts` 取 `result.reason.message` 原文（如 `SignatureDoesNotMatch`、`InvalidApiKey`）。顶层 `errorResponse` 有 `ERROR_HINTS` 中文映射（`app.ts:64-79`），但只作用于顶层错误，未下沉到 per-account。
- 【影响】多账号场景下单账号失败（密钥写错、权限不足）是高频事件，用户看到的是裸英文异常，无处置指引。
- 【建议】`runAccounts` 返回 `{ code, message }` 或在前端建立同样的 code→中文映射，复用 `ERROR_HINTS`。

**P1-7 移动端表格无收纳，6 列表格在手机上横向滚出屏幕**

- 【证据】`TokenPlanSection.vue:21-28` 座席表 6 列固定宽度合计约 690px（130+70+200+…），`AliyunSection.vue:14-18` 有效期列宽 220px；手机断点（e2e 用 375px，`dashboard.spec.ts:75`）下只能依赖表格容器横向滚动。
- 【影响】README:14 宣称「手机单列」可用，实际套餐 Tab 的核心数据（额度周期、剩余）在手机上需要来回横拖，体验断裂。
- 【建议】移动端将 t-table 切换为紧凑卡片列表（TDesign 无内置 card 模式，可用简单 v-for 列表或保留表格但收窄列集：移动端只显示「剩余/周期」两列）。

### P2 改进

**P2-1 顶部概览与正文口径不齐：status 只报 5 家，漏 Token Plan 与扩展平台；标签不可点击**

- 【证据】`server/app.ts:155-166` `handleStatus` 只返回 deepseek/volc/zhipu/aliyun/gitee；`App.vue:46-77` `providerTags` 同样硬编码 5 项。「火山方舟 ×2」的 count 是 AccessKey 数但驱动 2 个区块（plan+inference），语义混淆；标签无点击行为（不能跳转到对应卡片）。`App.vue:205` footer「数据来源」也漏扩展平台 6 家。（旧审查 P2 三连，均未修。）
- 【影响】用户无法从顶部判断「Token Plan / 扩展平台配没配」；标签只是装饰，不承载导航。
- 【建议】status 补 `tokenplan`/`extras` 聚合项；标签改为可点击（点击切换到对应 Tab 并滚动到卡片）；count 统一为「N 账号」语义。

**P2-2 刷新粒度全有或全无：无单板块重试**

- 【证据】任一区块错误只能等 60s 自动刷新或点全局「刷新」重发全部 9 接口（`dashboard.ts:66-107`）；`AccountSection.vue:25-27` 的 actions 槽只被 VolcUsageSection 的过滤框用过。
- 【影响】单点失败（某平台临时 5xx）恢复路径最短也要全量请求，浪费且慢。
- 【建议】区块头加重试按钮，store 按 slice 拆分单接口刷新方法。

**P2-3 自动刷新硬编码 60s 且默认开启，压力全给上游**

- 【证据】`dashboard.ts:29` `REFRESH_INTERVAL_MS = 60_000`，`autoRefresh = ref(true)`（:58），无间隔选项。每轮刷新是 9 个接口 × 各自多账号（`dashboard.ts:75-85` + 服务端 runAccounts 扇出）。
- 【影响】挂机一整天 = 8640 轮全量请求。对有速率限制的平台（火山管控面签名接口、阿里云 BSS）存在被限流风险，也不礼貌。
- 【建议】间隔下拉（30s/1m/5m/15m/关）+ localStorage 记忆；顺带把「自动/手动」开关文案改得更直白（现在 label 是 `['自动','手动']`，`App.vue:98`）。

**P2-4 重置倒计时文本在两次刷新间冻结，最长陈旧 60s**

- 【证据】`utils.ts:34-48` `formatReset` 用渲染时刻的 `Date.now()` 计算，无客户端计时器；数据每 60s 才重拉。
- 【影响】「2 小时 13 分后重置」会定格近一分钟，对盯着倒计时切换账号的用户有误导（5 小时窗口临近重置时尤其敏感）。
- 【建议】倒计时组件加 1 分钟粒度的客户端 tick（`setInterval(60s)` 重算格式化，不重拉数据）。

**P2-5 Tab 选择与过滤词不持久化，刷新即丢**

- 【证据】`App.vue:39` `activeTab = ref('subscription')` 无 localStorage；`modelFilter` 同样仅内存（`dashboard.ts:59`）。
- 【影响】用户固定关心「余额账户」Tab，每次打开页面都要手动切回。
- 【建议】两值均写 localStorage（theme 已有同款模式可抄，`theme.ts:36-47`）。

**P2-6 资源包类数据无进度可视化、到期无预警**

- 【证据】阿里云资源包（`AliyunSection.vue:79-106`）、Token Plan 座席/共享包（`TokenPlanSection.vue:145-201`）、智谱资源包（`ZhipuSection.vue:223-241`）全是纯数字表格，没有套餐窗口那样的 `t-progress`（对比 `VolcPlanSection.vue:125-129`）；到期时间仅作文本展示，临近到期（7 天内）无高亮。Gitee 代金券有状态标签但无「即将过期」档（`GiteeSection.vue:43-54` 只有已过期/可用/已用尽）。
- 【影响】「还剩多少」在资源包场景要心算 `remaining/total`；「什么时候必须用完」则完全没有信号——资源包过期即作废，这是真金白银的损失点。
- 【建议】资源包行内加迷你进度条（后端给的是字符串数值，前端 parse 后计算）；`expiryTime - now < 7d` 加 warning 高亮。

**P2-7 适老化声明与实现不符**

- 【证据】README:8 宣称「适老化字号基线」，但 `src/assets/main.css` 无任何字号规则（全文仅 reset + 字体栈），关键信息大量使用 12px `.muted`（重置倒计时、窗口脚注：`VolcPlanSection.vue` style、`AliyunSection.vue:124-126` 等）。
- 【影响】文案承诺了能力，实现没有兑现；12px 的次要色文字对视力较弱用户不友好。
- 【建议】要么删掉 README 的适老化表述，要么提供字号档位（normal/large）切换并放大 `.muted` 到 13-14px。

**P2-8 杂项一致性（多为旧审查 P3 未修）**

- Coding Plan 窗口 meta 左右都是百分比、无绝对值，与 AFP 窗口口径不一致（`VolcPlanSection.vue:177-180`）。
- `ExtraSection.vue:23` 副标题用「N 凭据」，其余区块用「N 账号」。
- Gitee Cookie 过期时只显示原始错误，不提示「Cookie 约 30 天需轮换，请更新 `GITEE_AI_SESSION_COOKIE`」（`GiteeSection.vue:147-153`；轮换事实只在 README:85）。
- `/api/status` 拉取失败时顶栏标签整行静默消失（`App.vue:118` `v-if`），无任何提示。

## 机会与缺失能力

| 能力           | 对标现状                                     | 本项目现状                                                          | 判断                                                                                                                                      |

## 结语

这次重构的执行纪律值得肯定：旧审查里「交互机制类」的问题（防抖、后台暂停、暗色、分组、响应式、标题/lang）基本清零，统一外壳和容错设计干净利落。但「产品语义类」的问题（空态、单位、别名、错误中文化）几乎原封不动，说明重构重心在框架迁移而非产品打磨——现在框架底座已经够好，没有借口再拖。下一轮只做一件事的主线：**让用户不用找，让异常自己跳出来**。P0 两条（摘要层 + 空态）加 P1 别名，合计一周以内的工作量，就能把这个项目从「好看的数据陈列柜」变成「真正的监控仪表盘」。
